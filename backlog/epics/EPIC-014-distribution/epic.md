# EPIC-014: ایمیج Docker فارسی، راهنمای نصب و فرایند ارتقا

## مسئله
- امروز نسخه‌ی فارسی فقط از روی کد این مخزن و با `yarn dev` بالا می‌آید. این روش برای توسعه است، نه برای یک شرکت که می‌خواهد NocoBase فارسی را روی سرور خودش نصب کند.
- کسی که NocoBase را از قبل دارد، راهی برای افزودن پلاگین فارسی ندارد.
- NocoBase تقریباً هر هفته وصله می‌دهد. هنوز یک بار هم ارتقای کامل (کلیدهای تازه‌ی ترجمه، آزمون تصویری، انتشار) تمرین نشده است.

## هدف و ارزش
- مدیر سیستم با یک فایل `docker-compose.yml` و کمتر از یک صفحه دستورالعمل، NocoBase فارسی را روی سرور خالی نصب می‌کند. بار اول برنامه با زبان فارسی، جهت راست‌به‌چپ و تقویم شمسی باز می‌شود.
- کاربر NocoBase موجود، فایل پلاگین را از صفحه‌ی انتشار دانلود می‌کند و از «مدیریت پلاگین» بارگذاری می‌کند.
- هر وصله‌ی NocoBase با یک فهرست کار روشن به نسخه‌ی فارسی تازه تبدیل می‌شود.

## دامنه
- ایمیج Docker بر پایه‌ی ایمیج رسمی همان نسخه‌ی `NOCOBASE_VERSION`، با پلاگین فارسی نصب‌شده و پیش‌فعال
- راهنمای نصب فارسی (سرور خالی، پشتیبان‌گیری، ارتقا)
- فرایند و ابزار ارتقای وصله‌ی NocoBase، و یک بار تمرین کامل آن
- نسخه‌گذاری و انتشار: GitHub Release با ایمیج، فایل پلاگین و یادداشت انتشار

## خارج از دامنه
- راهنمای کاربری کامل NocoBase به فارسی (فاز بعد یا اپیک جدا)
- نصب Kubernetes، خوشه‌ای یا چندسروری
- ارتقای فرعی یا اصلی NocoBase (مثلاً 2.3)؛ طبق [تصمیم ۰۰۰۲](../../../docs/decisions/0002-version-policy.md) اپیک جدا دارد
- انتشار پلاگین در npm یا بازارچه‌ی NocoBase

## معیار پذیرش اپیک
- [ ] روی سرور خالی با Docker، نصب از روی راهنما بدون دستور اضافه کار می‌کند و صفحه‌ی ورود فارسی است
- [ ] فایل پلاگین روی NocoBase رسمی همان نسخه بارگذاری و فعال می‌شود
- [ ] یک ارتقای وصله‌ی کامل با همین فرایند انجام و منتشر شده است
- [ ] هر انتشار در GitHub Release ایمیج، فایل پلاگین و یادداشت انتشار فارسی دارد

## وابستگی‌ها
- EPIC-008 تا EPIC-013 (آنچه در ایمیج می‌رود)
- [تصمیم ۰۰۰۲](../../../docs/decisions/0002-version-policy.md) (نسخه فقط در `NOCOBASE_VERSION`)
- گردش‌کار `nocobase-release-watch.yml` (STORY-003) که وصله‌ی تازه را خبر می‌دهد

## تصمیم: ایمیج روی ایمیج رسمی
ایمیج از روی ایمیج رسمی `nocobase/nocobase` ساخته می‌شود، نه از کد منبع. فقط پلاگین ساخته‌شده‌ی ما اضافه می‌شود.
- دلیل: ساخت از منبع زمان CI را چند برابر می‌کند. هسته هم هنوز وصله‌ای از ما ندارد (پوشه‌ی `patches/` وجود ندارد).
- اگر روزی وصله‌ی هسته لازم شد، این تصمیم بازبینی می‌شود.

## ریسک‌ها
- ایمیج رسمی ممکن است مسیر پلاگین‌ها یا متغیرهای پیش‌فعال‌سازی را در نسخه‌های بعد عوض کند. آزمون دود (smoke) در CI این را زود نشان می‌دهد.
- انتشار در GitHub Container Registry و ساخت Release کار بیرونی است و برگشت‌ناپذیر به حساب می‌آید. ساخت خودکار است، ولی برچسب‌زدن نسخه با صاحب پروژه است.

## پرسش‌های باز
- نام و جای ایمیج: پیش‌فرض `ghcr.io/baryuc40-collab/persian-erp` است. اگر صاحب پروژه نام یا Docker Hub دیگری بخواهد، فقط متغیر CI عوض می‌شود.
- شکل نسخه: پیش‌فرض `<نسخه‌ی NocoBase>-fa.<شماره>`، مثل `2.2.22-fa.1`. تصمیم نهایی در STORY-062 گرفته می‌شود.
